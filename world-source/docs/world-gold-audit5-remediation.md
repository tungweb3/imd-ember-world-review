## Trust and operating rules

- GOLD remains wallet-bound, nontransferable and nonredeemable; no AMM, sale-back, burn or staking-principal spending is added. Existing UTC staking rates, three owner wallets and simultaneous free/paid shared 2222 Mint rules remain unchanged. Game issuance is deferred.
- The treasury is one of the three existing administrator wallets. Administrators can publish immutable versioned prices, including economically generous prices, pause admissions and schedule/stop World-only trials. This is an existing trusted power; there is no arbitrary balance setter. The per-product/order 9007199254740991 GOLD bound is a JavaScript-safe-integer technical limit, not a total supply or issuance cap. Old valid orders retain their original entitlement and payment amount.
- Every account still has one int64 book balance; held and available are projections of that book. If an old lawful credit/refund cannot fit, it remains owed and visible in world_gold_reconcile_errors. A failure is not cancellation or permission to grant a different amount. Other orders progress; an explicit order retry can recheck the original after capacity is available.
- settleMintGold and finishGoldJob are internal server functions, with no browser facts route. Structured evidence is a validation/audit contract, not cryptographic proof by itself. Only deployment-pinned, canonical/finalized chain readers and authenticated real provider adapters may supply production facts. Session identity and allowance to spend remain separate from those authorities.
- The included Mint reader is PRIVATE EDR ONLY. Its proof includes a captured namespace, genesis/code anchors, original authorization, canonical receipt/events and chain clock. A process-local EDR loss cannot be repaired by restoring SQLite or labelling a new EVM with the old runId. Production needs a persistent, deployment-pinned namespace registry and finalized provider reader, plus an authenticated maintenance execution environment. Those must be validated before enabling production Mint integration; there is no public operator endpoint or arbitrary wallet-admin hold release.
- The delivery runner persists jobs and fences attempts. Production adapters must reuse orderId for upstream delivery/query, authenticate provider responses and retain provider nondelivery references. Exception, latency and lease expiry are unknown, never proof of non-delivery. A result that cannot be stored by World is a specific terminal World storage failure with a recorded reason and original refund; it is not presented as a provider-declared failure.
- Actual AIMarket/fortune result providers and VPS wiring are not included. No consumer is bound in the deployed Worker entry, so service admission remains closed even if a database flag is enabled. Runtime capability is trusted server wiring, never a browser or arbitrary environment flag. Existing pending work still has an independent reconciliation/refund tick.
- Migration0015 is additive; 0010..0014 are preserved. Backups must include all new tables/columns and original namespace/config identity. Restore into a separate reviewed copy, verify integrity and exact source, reconcile against the original chain authority, then review any migration/release batch. Historical recovery can inspect old known schema profiles without silently pretending they have the new production service integration.
- Real wallets, Ethereum mainnet runtime/finality, actual external results, production Workers CPU/D1 capacity, migration/rollback/postflight and public audit acceptance remain independent release gates. Production reviewedEconomyConfig still returns null. Local fixture success is not a release authorization.
